# SCRUM-76 / T38 — menu and price management

`/owner/menu` requires an active owner session. Search by name/code, filter by category/status, add an item, or open Edit. Item details and all size prices save in one transaction with Zod validation, integer cents, and an optimistic version check. Existing item codes/sizes remain stable because checkout rules and historical orders reference them.

Clear Available to order to mark an item sold out; it remains visible on the customer menu. Clear On the menu to archive it; restore by checking it again. Historical order names/prices never change. Hard deletion of items is intentionally unavailable under the existing data-retention rules. Empty categories can be removed; move all items first. Display order sorts items/categories ascending.

The editor shows recent price history (latest 200 changes across the menu), generated by the existing trigger. Saved changes invalidate customer menu routes. Sessions use RLS; no service-role writes. Apply the migration through the reviewed deployment process before using this page on hosted environments.

Patterns: Square item variations/table editing and Shopify's restrained operational dashboard structure. No dependencies added. Tests run in GitHub CI; database tests use a disposable database.

## Project lessons

- Menu prices live on `item_sizes`, not `menu_items`. Preserve size IDs and order snapshots.
- Archived items must be included in owner reads but excluded from public reads.
- Staff can change availability, but the menu editor and all its actions require owner access.
- Keep an editor's action feedback mounted across revalidation; refresh its version prop without resetting the form state.
- Next.js actions, pages and API routes can load separate module instances. Mutable local-demo menu data, versions and price history must share process-wide state; module-local arrays can report success while the next page read returns unchanged fixtures.
